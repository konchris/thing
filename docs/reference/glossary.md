# Glossary

Key terms used in THING documentation and artifacts.

| Term | Meaning |
| --- | --- |
| Stakeholder | Any person, role, or organization with an interest in the system. |
| Stakeholder Need | A problem, expectation, or desired outcome from a stakeholder perspective. Needs are not requirements — they are the raw material from which requirements are derived. |
| Concept of Operations (ConOps) | Description of how the system is expected to be used in operational context — who uses it, under what conditions, in what modes, and with what success criteria. |
| Non-Functional Requirement (NFR) | A requirement describing a quality, constraint, or system property rather than functional behavior. Covers categories from ISO/IEC 25010: performance, reliability, security, usability, maintainability, portability, and others. |
| Functional Requirement (FR) | A requirement describing what the system must do — a specific capability or behavior. |
| Set-Based Design | An approach that explores and preserves multiple solution options in parallel until evidence supports convergence on one. Options are eliminated only when evidence — not opinion — rules them out. |
| Phase Gate | A review checkpoint at the boundary between workflow phases. The gate performs a binary pass/fail check before the workflow may proceed. No phase closes until its gate passes. |
| Requirements Traceability Matrix (RTM) | An artifact mapping each requirement to its source, design allocation, implementation reference, and verification case. Initiated at Phase 2 and updated through Phase 6. |
| Verification | Confirmation that the system satisfies its specified requirements. Answers: did we build the system right? |
| Validation | Confirmation that the system solves the stakeholder's actual problem. Answers: did we build the right system? Passing verification against a wrong specification is not success. |
| V&V Plan | The combined Verification and Validation plan. Initiated at Phase 1, updated with each requirement, and finalized at Phase 6. |
| Interface Control Document (ICD) | A document defining all interfaces at every system boundary — inputs, outputs, protocols, data formats, and interaction constraints. |
| Architecture Decision Record (ADR) | A dated record of a significant architectural choice, including context, decision, rationale, and consequences. |
| Threaded Artifact | An artifact that is initiated at a specific phase and updated continuously as an obligation of each subsequent phase. The risk register, V&V plan, and RTM are threaded artifacts. |
| Sequenced Artifact | An artifact created at a defined phase with a clear completion state. Consumed as input by later phases. |
| Constitution | The governing document establishing domain context, standards, development principles, and SE workflow obligations for a project. Updated whenever governing principles change. |
